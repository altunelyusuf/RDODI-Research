Architectural Pillar

Staples (2026) argues that trust, once code stops being the constraint, has to be built into an enterprise platform rather than assumed of any single model. He names four architectural capabilities an organization needs to hold that trust: an agent platform, machine-scale execution, durable context, and governance. Each is described below with the concrete GitLab product Staples cites as its implementation, alongside the independent evidence found for the same capability at Stripe, Spotify and Amplitude.

Agent Platform Pillar

The agent platform pillar is the capability to create, customize and operate agents an organization owns, on models and infrastructure it chooses, while also supporting agents brought from other vendors. Staples (2026) presents GitLab Duo Agent Platform as the concrete implementation, and states explicitly that a customer running Claude Code should be able to keep running it with the same enterprise context, identity and audit trail as any agent GitLab builds itself. Stripe's minions (Gray, 2026) are an independently documented instance of an organization building and owning its own agents rather than depending solely on a vendor's, combining deterministic blueprint nodes with agent loops.

Exemplar: GitLab Duo Agent Platform as the Agent Platform pillar — source: code_abundance_research_v1_0_0.ttl#ca:Staples2026WhenCodeAbundant

Context Pillar

The context pillar is a coherent, persistent picture of requirement, code, history, priority and constraints surrounding a piece of work, so that an agent can query relationships directly instead of reconstructing them through disconnected calls. Staples (2026) names GitLab Orbit as this pillar's implementation, connecting code, work items, pipelines, deployments and production signals into a graph usable by third-party agents as well as GitLab's own. Spotify's Honk illustrates the cost of the opposite condition: at QCon London 2026, Kelly-Fenton and Mitic reported that inconsistent pipeline frameworks across Spotify's codebase made reliable automated migration far harder than where frameworks were standardized (Curtis, 2026), a direct empirical instance of what happens when this pillar is missing.

Exemplar: GitLab Orbit as the Context pillar — source: code_abundance_research_v1_0_0.ttl#ca:Staples2026WhenCodeAbundant

Execution Pillar

The execution pillar covers next-generation source control, artifact management and CI/CD able to build, test, deploy and operate software at machine scale. Staples (2026) reports GitLab's own next-generation source control producing task execution up to 50 times faster in internal testing by letting an agent retrieve only what a task requires rather than repeatedly moving an entire repository. Amplitude's independently reported pipeline overhaul points at the same pillar from the demand side: pull-request cycle time and frontend CI both fell sharply once the pipeline itself, not the model, was rebuilt (Staples, 2026), a claim this report was only partly able to verify against Amplitude's own public materials (see Cost Per Accepted Change and the Stage 1 quality scorecard for the specific figures flagged unavailable).

Exemplar: GitLab's next-generation source control as the Execution pillar — source: code_abundance_research_v1_0_0.ttl#ca:Staples2026WhenCodeAbundant

Governance Pillar

The governance pillar enforces boundaries around security, compliance, quality, identity and permissions, and gives people visibility into what agents did and why an action was permitted. Staples (2026) argues governance, not model capability, is the binding constraint on how far autonomy can safely go, a claim Stripe's own account supports directly: minions combine open-ended agent loops with deterministic checks for git, linting and testing, running in isolated environments and selectively executing tests from a suite of more than three million (Gray, 2026). Whether this pillar is adequate is itself a live question in the trade press: independent commentary on GitLab's concurrent Act 2 restructuring questioned whether the same governance rhetoric was compatible with using agents to automate the approvals GitLab's own workforce previously performed (The Dev Loop, 2026).

Exemplar: GitLab's Governance for Agents as the Governance pillar — source: code_abundance_research_v1_0_0.ttl#ca:Staples2026WhenCodeAbundant

Development Mode

Staples (2026) rejects a single maturity curve from traditional to fully autonomous development, arguing three modes will coexist for a long time. He offers a practical diagnostic distinguishing them: whether an agent can make a useful change with available context, whether that change can be verified without a person reading every line, and whether the system catches an error or a person must. The three modes are described below with the industry cases that best exemplify each.

Agentically Accelerated Mode

Mode 2 keeps humans in control while agents assist with implementation, testing, migration, review, documentation and security analysis, and Staples (2026) claims this is where most enterprise development sits today and where he expects most near-term economic value. Amplitude's own reported experience -- designers, product managers and marketers going from roughly zero to about five percent of pull requests (see Cursor, 2026, cited under Builder Role) -- sits squarely in this mode: humans direct and evaluate, agents execute, and the boundary between deciding what to build and building it narrows without disappearing.

Exemplar: Most enterprise development today, per the article — source: code_abundance_research_v1_0_0.ttl#ca:Staples2026WhenCodeAbundant

Autonomous Mode

Mode 3 has agents operate the implementation loop while humans provide intent, constraints and oversight, and Stripe's minions are the clearest documented instance in this corpus: independent trade coverage reports minions merging roughly 1,300 human-reviewed pull requests per week that contain no human-written code at all (InfoQ, 2026). Staples (2026) is explicit that reaching Mode 3 for a given workload depends on governance and verification infrastructure being in place first, not on model capability alone, a claim consistent with Stripe's own description of the deterministic checks wrapped around its agent loops.

Exemplar: Stripe's minions as a Mode 3 example — source: code_abundance_research_v1_0_0.ttl#ca:StripeMinionsPart1_2026

Human-Controlled Legacy Mode

Mode 1 covers systems with undocumented dependencies and operational knowledge that still resides in people, which Staples (2026) expects to remain largely human-controlled until retired or rewritten. No industry case in this corpus documents a organization deliberately choosing to keep a system in this mode as a strategic decision rather than as an unaddressed legacy burden, which is itself consistent with the article's framing: Mode 1 is presented as a residual category rather than a destination.

Economic Reframing

Staples (2026) argues that AI is not simply making programmers faster; it is displacing the variable that organized software engineering for sixty years. Where cost and risk once concentrated in the act of writing code, the article claims that concentration is moving to the act of trusting what was written. This section introduces the two concepts that carry that argument: the historical constraint being broken, and the new unit proposed to replace it.

Code-Is-Precious Constraint

For sixty years, Staples (2026) writes, software engineering organized itself around the premise that code is precious: expensive to produce because it requires scarce people who can hold complex abstractions in their heads, and fragile because small mistakes compound. He traces much of the discipline's ceremony -- reviews, approval gates, tolerated technical debt, the premium placed on developer productivity -- to this single constraint. The claim under scrutiny in this report is not that the constraint is loosening, which is well evidenced by the industry cases in the next sections, but whether its removal actually reduces the total work of engineering, addressed directly under Cost Per Accepted Change below.

Exemplar: The sixty-year 'code is precious' constraint — source: code_abundance_research_v1_0_0.ttl#ca:Staples2026WhenCodeAbundant

Cost Per Accepted Change

Staples (2026) proposes replacing cost-per-line-of-code with cost-per-accepted-change: a unit bundling generation, environment setup, context, verification, review, remediation and governance. He invokes the Theory of Constraints (Goldratt, 1984) directly to argue that collapsing the generation term alone does not collapse the total cost; an organization that makes generation ten times faster while leaving CI, review and validation untouched, in his words, 'will simply move the queue.' Read against Jevons (1865), whose paradox holds that efficiency gains in a resource tend to increase rather than decrease aggregate consumption of it, the reframing gains an alternative reading: cheaper generation may not just relocate cost within a fixed volume of work, but expand the volume of work attempted in the first place, a distinction the article's own case evidence (Section: Industry Implementation) does not fully resolve.

Industry Implementation

Staples (2026) anchors his argument in four concrete, named systems: an open format for agent context, and three organizations' production coding agents. Each is documented below against the independent sources this research corpus was able to verify, including one figure Staples (2026) cites that could not be independently confirmed.

AGENTS.md Format

AGENTS.md is an open format for providing project instructions and context to coding agents. Staples (2026) cites GitLab's support for it as an example of a broader principle he states directly: an organization's accumulated operating knowledge should remain portable if the organization changes models, agents or vendors, and the principle matters more than the specific filename.

Exemplar: AGENTS.md as supported by GitLab — source: code_abundance_research_v1_0_0.ttl#ca:Staples2026WhenCodeAbundant

GitLab Duo Agent Platform

GitLab Duo Agent Platform is GitLab's own platform for creating, customizing and operating agents around an organization's workflows and expertise, letting customers choose the underlying models and infrastructure. Staples (2026) presents it as the concrete implementation of the Agent Platform pillar described earlier in this report; independent trade coverage of GitLab's concurrent Act 2 restructuring notes the same period saw GitLab move to consumption-based pricing for agent work, indicating this platform also carries a direct commercial stake for GitLab as its vendor (InfoWorld, 2026).

Exemplar: GitLab Duo Agent Platform (the product) — source: code_abundance_research_v1_0_0.ttl#ca:Staples2026WhenCodeAbundant

Honk (Spotify)

Honk is Spotify's background coding agent for continuous, large-scale code migration. Staples (2026) documents more than 1,500 AI-generated pull requests merged into production; independent reporting from Spotify's QCon London 2026 talk gives a throughput figure of roughly 1,000 merged pull requests every 10 days, and states Honk was built specifically to handle the long tail of migration edge cases that Spotify's prior deterministic scripts could not resolve (Curtis, 2026).

Exemplar: Spotify's Honk system — source: code_abundance_research_v1_0_0.ttl#ca:InfoQSpotifyHonk2026

Minions (Stripe)

Minions are Stripe's homegrown, unattended coding agents. Stripe's own engineering blog describes them as responsible for more than a thousand pull requests merged weekly, with humans reviewing but not writing the code (Gray, 2026); independent trade coverage later reported the figure at roughly 1,300 per week (InfoQ, 2026). The system combines deterministic 'blueprint' nodes with agent loops, running in isolated devbox environments and selectively executing tests from a suite exceeding three million, which Staples (2026) cites as evidence that reliability at this scale comes from infrastructure built around the model, not from the model alone.

Lifecycle Model

Staples (2026) argues that as AI compresses the traditional plan-build-test-secure-deploy-operate sequence into continuous agentic loops, the boundary between developing software and developing the product itself blurs. This section covers the single named model he proposes for what replaces the conventional SDLC.

Product Development Lifecycle

Staples (2026) proposes the Product Development Lifecycle, or PDLC, as the successor to the SDLC: business intent enters the system, agents turn it into software, verification and governance determine what can proceed, and production results feed back into the next decision. He positions this against Anthropic's contemporaneous AI-Native SDLC Playbook, published three days before his article, which reorganizes the same six traditional stages around versioned, machine-readable Markdown artifacts rather than replacing the SDLC concept outright (Claxton, 2026); the two proposals converge on continuous, artifact-driven loops even where their vocabulary differs.

Exemplar: GitLab's proposed Product Development Lifecycle — source: code_abundance_research_v1_0_0.ttl#ca:Staples2026WhenCodeAbundant

Organizational Role

As implementation gets cheaper, Staples (2026) argues the boundary between deciding what to build and building it starts to collapse, and proposes a broadened role for the people who do that work. This section covers that role and the evidence offered for it.

Builder Role

Staples (2026) proposes 'Builder' as a role covering anyone -- engineer, designer, product manager, security expert, marketer or domain expert -- who can express intent, direct agents, evaluate results and turn an idea into working software. His evidence is Amplitude's reported experience of designers, product managers and marketers going from essentially zero pull requests to roughly five percent after Amplitude improved its development setup, validation and review (Cursor, 2026). He is careful to add that engineering judgment does not become abundant because implementation does; scarce human attention, in his account, moves upward toward architecture, intent and difficult exceptions rather than disappearing, a claim this report was not able to test independently against data broader than the single five-percent figure cited.
